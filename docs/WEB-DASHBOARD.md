# Web dashboard in TypeScript: plan

**Status: in progress since 2026-11-01** (phase 0 done). Written for after the rename to
Undercurrent ([RENAME.md](RENAME.md)), so it uses the new names: the package
`undercurrent`, the command `undercurrent web`, Grafana uids `undercurrent-*`. Until the
rename lands, the code keeps today's names (RENAME.md §2).

The web dashboard of `85b365c` (2026-10-31) is a plainer view of what the Grafana dashboards
show: a Python server with 19 JSON endpoints and a page in plain JavaScript with Preact
vendored, no build step. It was the fastest way to get a second view next to Grafana. This
plan rebuilds the page in TypeScript on a stack meant to last years, with charts that are
actually good, and turns it from "Grafana, plainer" into the place where everything the
system knows about a term, a channel, a story or a product is one click from everything
else. Grafana stays as the pro mode until the user picks one of the two (§11.3).

What changes, in one paragraph: the page becomes a React and TypeScript app in `web/`, built
by Vite, styled with Tailwind and shadcn/ui, with TanStack Router for URLs and TanStack
Query for data. Charts use Apache ECharts behind a small kit of our own, themed from the
same validated palette as today. The Python server stays, moves to FastAPI, and describes
every response with a Pydantic model, from which the TypeScript types are generated. So the
statistics stay in Python, and the types are checked from the ClickHouse row to the pixel.
On top come pages per entity (term, scope, story, edge, product), cross-filtering between
charts, a command palette, URL state for every view, and a list of things Grafana can't do:
a replay of how a story spread, switching flows, a "why is this trending" explainer, rank
and rhythm charts, co-occurring terms, time travel.

**It costs nothing to run**, like the rest: every library is free and open source, the built
page is static files served by the Python server that exists today, and no new service runs
in production.

## 3. Stack

### 3.1 What "future proof" means here

The page will be maintained for years by one person and by AI agents, and run on one small
machine. So:

* **Boring and big.** The stack an agent has seen most and gets right without docs, with
  libraries that will still be maintained in five years. A smaller, nicer framework loses
  if agents write it worse.
* **No server-side JavaScript in production.** Server rendering helps search engines and
  first paint on slow phones; a personal dashboard behind a password needs neither. Static
  files mean no Node runtime to patch, and no framework whose server model changes every
  major version.
* **Types end to end**, so an agent's change that breaks a contract fails `tsc` or CI, not
  the page.
* **Few dependencies, pinned**, updated on purpose. The npm ecosystem had several
  self-replicating supply-chain attacks in 2025; every dependency is a risk.
* **Owned UI code.** shadcn/ui copies component source into the repository, so an upstream
  redesign never breaks the page; we update when we choose.

### 3.3 The pick

**React 19 + TypeScript + Vite, a static single-page app.**

* React because of the ecosystem: shadcn/ui, TanStack, every chart library, testing tools,
  and the most training data. Since February 2026 it belongs to the React Foundation under
  the Linux Foundation instead of Meta, which is about as safe as a front-end library gets.
  The React Compiler (stable since 1.0) removes most hand-written memoization, which is
  where agents make subtle mistakes.
* Vite because it is the default build tool of everything but Next.js, fast (Rolldown since
  8), and its dev proxy fits a Python API (§9.3). Cloudflare owning it since June 2026
  changes nothing for us while it stays MIT; Vite is too widely used to vanish.
* A single-page app because nothing needs a server: the data comes from the Python API and
  the page is behind a password. Routes are code-split, so the first page stays small. If
  server rendering is ever wanted (a public report page, say), TanStack Start 1.0 adds it on
  the same router, without a rewrite.

**Why not the others:**

* **Next.js** is built around server components and its own server or Vercel. As a pure
  static export it loses most of what it's for and keeps its weight, and its conventions
  (caching, routing, server actions) changed with every major version. We'd run a Node
  server, or a crippled export, for no gain.
* **SvelteKit 3 with Svelte 5** is the runner-up: smaller bundles, less code, a static
  adapter, `shadcn-svelte`, and the best first-party help for agents of any framework (an
  official MCP server and llms.txt). It loses on the size of the ecosystem around tables,
  charts and testing, on how reliably agents write runes-era Svelte (most of the Svelte
  they've seen is Svelte 4), and SvelteKit 3 just changed its config and import paths again.
* **SolidJS** is fast and pleasant but small, with 2.0 still a release candidate and its
  meta-framework in flux; **Vue/Nuxt** would work and offers nothing React doesn't here;
  **Astro** is for content sites; **Remix 3** left React; **React Router 8** is a fine
  router with a SPA mode, but its search params aren't typed like TanStack Router's and it
  now ships a major every year.
* **Staying on Preact without a build step** keeps the page tiny, but shadcn/ui needs React
  (through `preact/compat` it half works), and TypeScript needs a build anyway.
* **Server-rendered HTML with htmx** would keep everything in Python, but the user asked for
  TypeScript, and brushing, cross-filtering, a replay and a command palette are client work.

**Around React:**

* **TanStack Router** (file-based routes, code splitting): every route declares its search
  params as a Zod schema, so url state is typed, validated and defaulted in one place
  (§6.7). Loaders prefetch the route's queries.
* **TanStack Query**: one cache, keys from the API path and parameters, previous data kept
  while refetching (the dataviz rule "refetch keeps the frame"), invalidation from live
  events (§5.3).
* **TanStack Table** 9 with **TanStack Virtual** for the big tables (trends, edges,
  comments).
* **shadcn/ui** on **Tailwind CSS v4**: buttons, inputs, popovers, sheets, tabs, toggle
  groups, tooltips, hover cards, the command palette (`cmdk`), date range presets, data
  tables. Copied into `web/src/components/ui/`, owned and edited like our own code. On
  shadcn's default primitives (Radix); Base UI is the alternative shadcn supports, chosen
  per component, if Radix stalls.
* **Tailwind's company is the weakest link** (§3.2): most of its engineers were let go in
  January. Tailwind is a build-time tool used by millions of projects, so it won't stop
  working, and it's used here only for utility classes over our own CSS variables. If it
  stagnates, the tokens and components move to plain CSS without touching the charts or the
  data layer.
* **Zod** for search params and for parsing anything not covered by generated types
  (localStorage, SSE payloads).
* No global state library: the url holds view state, the query cache holds server state,
  and a few preferences (theme, density) live in a small hook over localStorage.

### 3.4 Tooling

* **pnpm** 12, pinned through `packageManager` in `package.json`. It doesn't run
  dependencies' install scripts unless allowed, and its minimum release age (24 hours by
  default, raised to 3 days here) keeps freshly published versions out for the window in
  which compromised packages have been caught so far. Bun would do as well; pnpm on Node is
  what the rest of the tooling assumes.
* **Node 26**, the current LTS (supported to April 2029), pinned in `.nvmrc` and `engines`,
  used for building and tests only.
* **TypeScript 7**, the native compiler, in strict mode with `noUncheckedIndexedAccess` and
  `exactOptionalPropertyTypes`. `tsc --noEmit` is the type check and takes seconds. Until
  7.1 brings a stable programmatic API, a tool that needs it pins TypeScript 6 for itself.
* **Oxlint** for linting, with its type-aware rules (floating promises, misused promises,
  unsafe `any`, unnecessary conditions): the mistakes agents make in async React code.
  typescript-eslint would be the classic choice, but it doesn't run on TypeScript 7.
* **Biome** for formatting only: Prettier's output at a fraction of the time, one config
  file. Biome's linter alone is the fallback (fewer type-aware rules), and if Oxc's
  formatter reaches 1.0, one tool could do both.
* **Vitest** for unit and component tests, **Playwright** for end-to-end tests,
  **`@axe-core/playwright`** for accessibility checks.
* **Renovate** or Dependabot, grouped weekly, for npm, Python, Docker images and Actions.

Oxlint, Vite and Vitest come from the same company (VoidZero, now Cloudflare's), which also
sells an all-in-one wrapper, Vite+. The plan uses the tools directly, not the wrapper, so
any one of them can be swapped.

`tsconfig.json` sets `"types": ["vite/client"]`, so stray `@types` packages above `web/`
(v1's leftovers) are never picked up.

### 3.6 Written for agents

`web/AGENTS.md` (and the README's development section) says what an agent can't infer:

* The commands: `pnpm dev`, `pnpm check` (types, lint, format, unit tests), `pnpm e2e`,
  `pnpm gen:api`.
* `src/api/generated/` is generated. A change to the API's data is a change to a Pydantic
  model, then `pnpm gen:api`, never an edit of the types.
* `shadcn docs <component>` and `shadcn info` before adding or changing a component (the
  CLI answers for the version in use), and components are added with the CLI, then edited.
* Every view's state lives in its route's search schema; nothing that changes what's shown
  lives only in component state.
* Charts go through the chart kit, colors through tokens. No hex values in components, no
  chart library imported outside `src/charts/`.
* Every new endpoint comes with a model, a test on the schema, an entry in the web
  benchmark (§10.4) and its cost written next to it.
* Empty states say why they're empty and when data will come (§8.4).

## 4. Charts

### 4.1 What they must do

From the data and from the dataviz method (palette, mark specs, interaction rules):

* Time series of shares with many series, a crosshair listing every series, annotations
  (alerts, onsets, forecast windows, long-term windows), a brush that sets the time range,
  and crosshairs linked across charts and small multiples.
* Heatmaps (hour of week, leader × follower lags), a calendar heatmap, a bump chart of
  ranks, flows (Sankey and chord), a network with a replay over time, distributions (lags,
  probabilities), a calibration plot, dumbbells and slopes, small multiples.
* Light and dark modes as selected palettes, not inverted colors; a legend for two or more
  series and direct labels where they fit; a table view for every chart; texture for color
  vision deficiency, print and forced colors.
* Fast enough for a year of daily points times a dozen series, and for 46 small multiples on
  a phone.
* Testable without a browser, so agents can check what they changed.

### 4.3 The pick: ECharts, behind our own kit

**Apache ECharts 6** is the only library that covers every form of §4.1 in one engine with
interaction built in:

* Lines, areas and bars with `markLine`, `markArea` and `markPoint` annotations; `dataZoom`
  and `brush` for selecting a range; `echarts.connect` for crosshairs and tooltips linked
  across charts.
* Heatmap, calendar, Sankey, chord (new in 6), graph (force or fixed layout), box plot,
  parallel, custom series for anything else (a bump chart is lines on an inverted rank axis,
  a dumbbell is a custom series).
* Canvas rendering by default, SVG on request, and a server-side renderer: in Node,
  `renderToSVGString` turns an option into an SVG string, so a unit test can render a chart
  and an agent can look at it.
* `aria` with generated descriptions and `decal` patterns, the texture channel of the
  dataviz method.
* Themes are objects, registered at runtime; ours is built from the CSS tokens (§4.5) and
  switched with the page's theme.
* A foundation project (Apache) with a large, active community and more than a decade of
  releases; 6.0 came in July 2025, 6.1 in May 2026.

It is used directly, not through `echarts-for-react` (a thin wrapper whose releases have
slowed): a `<Chart option={…} />` component of about 80 lines (`init` on mount, `setOption`
on change, `ResizeObserver`, theme switch, dispose, `connect` group) and `echarts/core`
with only the charts and components we use, loaded with the routes that use them.

The kit (`web/src/charts/`) is what pages use. Each chart is a pure function from typed data
to an ECharts option, plus a React component that adds the frame: title, subtitle, help,
legend, table view, export and the "Pro mode" link. Option builders are where the dataviz
rules live (thin lines, 4 px rounded bar ends, hairline grid, one y axis, direct labels for
up to 4 series, tooltips that lead with the value), so pages can't break them.

**What isn't ECharts:**

* **Sparklines, meters and inline bars** in table cells stay tiny SVG components (the
  current `Sparkline` in TypeScript). 200 rows of ECharts instances would be 200 canvases.
* **The stat tile and hero number** are HTML, per the dataviz method.

**Why not the others:**

* **shadcn charts (Recharts)** look native next to shadcn/ui and suit simple bars and lines,
  but have no heatmap, calendar, chord or network, and render SVG only. Two engines would
  mean two themes, two tooltip styles and two sets of rules; one engine keeps the charts one
  system. The look shadcn's charts have (thin lines, soft grid, rounded bars, quiet
  tooltips) is a theme, and the kit reproduces it in ECharts.
* **visx** (or plain d3 in React) gives the most control and the most on-brand result, but
  every form is code we'd write and maintain: Sankey layout, force layout, brushing,
  tooltips, canvas fallbacks. And its 4.0 in June 2026 was its first release in 19 months;
  d3-sankey hasn't changed since 2019.
* **Nivo** has nearly every form (bump, calendar, chord, Sankey, network, swarm) as React
  components, but little interaction (no brushing or zoom, no linked crosshairs), and no
  release since May 2025.
* **Observable Plot** is the best for quick small multiples and exploratory charts, but has
  no flows or networks, minimal interaction, and no release since February 2025.
* **uPlot** is the fastest time series library there is, and only that, by one maintainer.
* **Highcharts** isn't open source (free only for personal, non-commercial use), and
  **AG Charts** keeps Sankey and chord in its paid edition; both rule themselves out under
  "everything free and open source". **Plotly** is heavy, looks like a notebook, and has a
  "send to Plotly Cloud" button on by default; **Chart.js**, **Victory** and **Unovis** lack
  forms; **Tremor** is frozen.

**Networks.** The leader → follower graph is small: 46 channels plus groups and, later,
platforms, at most a few hundred edges. ECharts' graph series draws it with positions we
compute (§7, the spread map), so the layout means something instead of floating. Kept in
reserve: **sigma.js** 4 with graphology (WebGL2) if a term network ever grows into thousands
of nodes, and **d3-force** for computing a layout without drawing it (finished software, not
abandoned). **React Flow** is for editable diagrams of boxes and wires, not data networks,
and **Cytoscape.js** brings its own look and a second engine, so neither fits.

### 4.5 Color and theme

Colour is the brand's ([BRAND.md](BRAND.md) §5, accepted 2026-11-01), which replaced the
dataviz reference palette this section first named: the tokens of
`web/src/styles/tokens.css` (moved from `docs/brand/`), exposed as Tailwind v4 `@theme`
utilities.

* Categorical, 8 slots in fixed order: teal, rust, violet, amber, magenta, green, blue,
  red, with light and dark steps validated against each theme's chart surface (BRAND.md
  §5.5). Forms where every pair can meet (scatter, small multiples colored by series) use
  at most 3 slots; past 8 series the tail folds into "Other".
* Sequential Current (`seq-100` … `seq-900`) for magnitude, diverging rust ↔ gray ↔
  Current (`div-neg-3` … `div-pos-3`) for signed values, status good, warning, serious,
  critical always with an icon and a word (BRAND.md §5.4).
* Surfaces, ink, gridlines and baselines from the semantic tokens (`bg`, `surface`, `ink`,
  `chart-grid`, `chart-axis`, `chart-band`; BRAND.md §5.3).
* **Color follows the entity.** A term or scope gets its slot from a stable assignment for
  the page (by order of first appearance in the page's primary list, kept in the url when it
  matters), so filtering never repaints the survivors.

The ECharts theme (`web/src/charts/theme.ts`, from `docs/brand/`) reads the tokens
with `getComputedStyle` at runtime and is rebuilt when the theme changes, so CSS stays
the single source. Any palette change re-runs the dataviz validator in both modes, and a
unit test pins the token values so they can't drift silently.

### 4.6 Interaction rules

* Line and area: a crosshair snapping to the nearest bucket, one tooltip with every series,
  values first. Bars, cells, nodes: the mark is the hit target, at least 24 px.
* Hovering a row in a table highlights its series in the charts (others go gray, the
  dataviz "emphasis" form), and the other way round.
* Brushing a time range on the main chart of a page sets the page's `from` and `to`; every
  chart, stat and table below follows.
* While data reloads, charts keep their last render at reduced opacity. Skeletons only on
  the first load.
* Keyboard: every chart frame is focusable; arrow keys move the crosshair, Enter opens the
  hovered entity, `t` toggles the table view.

### 4.7 Budget

* First page under 250 KB of compressed JavaScript; ECharts loads with the first chart and
  only the series types a route uses.
* A chart renders in under 100 ms on a mid-range phone for 12 series × 400 points.
* No chart query over 1 s at production scale (§7.2 and §10.4).

## 5. API

### 5.1 Python or TypeScript on the server

**Keep the API in Python.** The alternative, a TypeScript server (Hono with the official
ClickHouse client, Zod and tRPC or Hono's typed client), would give types end to end without
code generation. But:

* What the dashboard shows comes from Python: scopes and groups from `config.yaml`, the
  gates of every detector (min mentions, authors, ratios, per scope and kind), the intent
  kinds, platform priors, and the statistics themselves (`score_arrays` for the explainer
  and the replay, log odds for co-occurring terms). A TypeScript server would duplicate them
  or call Python anyway.
* The SQL already lives in Python, tested against throwaway ClickHouse databases; the
  Grafana builder is Python too.
* Two servers would mean two places to keep read-only, authenticated and fast.

Types stay checked end to end through the API's schema:

1. Every endpoint returns a **Pydantic model** (times as UTC datetimes, nullable where the
   data can be missing).
2. FastAPI produces the **OpenAPI 3.1** schema; `undercurrent web openapi` prints it, and
   it's committed as `web/src/api/openapi.json`.
3. **orval** generates from it the types, a small `fetch` client and a TanStack Query hook
   per endpoint, with query keys derived from the path and parameters, and Zod schemas for
   checking responses in tests and in development builds.
4. CI exports the schema, regenerates the client and fails on any difference, so a server
   change that the page doesn't know about can't be merged.

**orval over openapi-typescript:** `openapi-typescript` with `openapi-fetch` is the
leaner pair (types only, a few KB of client), but it hasn't been released since February
2026, and it builds its output with TypeScript's compiler API, which TypeScript 7 doesn't
offer as stable yet. orval is actively released, writes the hooks we'd otherwise write by
hand, and generates Zod schemas from the same source. Both read the same schema, so
switching back costs a regeneration and the call sites. `@hey-api/openapi-ts` (still 0.x,
slowing) and Kubb were the other candidates.

**FastAPI over Litestar:** both are typed and generate OpenAPI. Litestar is faster and
arguably cleaner, but its 3.0 is announced and not out; FastAPI (0.162, on Starlette 1.0)
is what agents know best and what most examples use, ships server-sent events itself, and
at this traffic speed doesn't matter. Endpoints are plain `def`, run in FastAPI's thread
pool, with the same session-less `clickhouse-connect` client as today (its native async
client exists since 1.0, but a thread pool is simpler and enough). `uvicorn` serves it.

### 5.2 From panels to resources

Today's endpoints follow Grafana's panels. The new ones follow the entities of §6.1, under
`/api/v1/`, so pages can combine them and links can point at them:

| `GET /trends` | the latest (or `as_of`) run of a scope and horizon, with 7-day sparklines | `trends`, `term_hourly` |

| `GET/PUT/DELETE /pins`, `/views` | pinned terms and saved views (§7, phase 5) | `web_pins`, `web_views` |

Conventions:

* **`now` is a parameter of every query.** Today the SQL calls `now()` and `today()`
  directly. In the rebuild every query takes `{now:DateTime}`, by default the current time.
  That makes tests and the demo database deterministic (§10), and gives time travel for
  free: `?as_of=2026-12-01T12:00Z` shows any page as it was then, as far as the stored
  history goes (§7.1, item 16).
* **A term is the rest of the path** (`/terms/repo/ollama/ollama`), so terms with slashes,
  like cross-platform's `repo` kind, need no escaping; the same holds for the page's
  `/t/{kind}/{term}`.
* **Missing is `null`**, never 1970-01-01: `max()` of nothing becomes `NULL` in SQL
  (`maxOrNull`), and models say which fields can be missing.
* Times are UTC with a `Z`, days are ISO dates; numbers that can be infinite or NaN are
  `null`, as today.
* Errors are `{"error": "…"}` with 400 (bad parameters), 404 (unknown scope or term), 502
  (ClickHouse failed) and 504 (the query hit its time limit).
* Every query sets `log_comment` to its endpoint, so `system.query_log` shows what each
  endpoint costs in production (§10.4).
* Responses carry `Cache-Control: max-age` matched to what they read: 60 s for trends (the
  analyzer runs every 15 minutes), a day for closed events, none for ingestion. A small
  in-process cache (15 minutes, keyed by the full query) covers the expensive endpoints
  (co-occurring terms, a scope's distinctive vocabulary).

### 5.3 Live updates

`GET /api/v1/stream` is a server-sent events stream. One background task in the API asks
ClickHouse every 30 seconds what changed: the latest `detected_at` per horizon, the latest
long-term week, the latest edges day, new rows in `notifications`, and (every 10 seconds,
only while a client watches the Collection page) the newest poll. It sends `run`, `alert`,
`forecast`, `edges` and `ingest` events to every open tab, and the page invalidates the
queries that depend on them: a new run refreshes Trending, a new alert shows a toast that
opens the term page.

One query every 30 seconds costs the same whether one tab or ten are open. SSE goes through
basic auth like any request, reconnects on its own, and needs no WebSocket server; FastAPI
has it built in (`fastapi.sse`, since 0.135), so it adds no dependency. If the stream is
down, queries fall back to refetching on focus and every 5 minutes.

### 5.4 Auth

* **Basic auth** with `WEB_PASSWORD`, as today, for the page, the API and the stream; the
  server keeps listening on localhost unless `--host` says otherwise. It works in every
  browser, with `curl`, and with `EventSource`.
* **Beyond localhost**, put something in front instead of building auth: Tailscale (the
  phone and the server in one private network, `tailscale serve` for TLS), or a reverse
  proxy with TLS (Caddy). Either also covers Grafana and ntfy. A login page, sessions and
  OAuth are for when someone else uses it (the churn radar's customers), and then
  `oauth2-proxy` or Authelia in front is still less code than our own.
* **Writes** (pins, saved views; phase 5) only accept `application/json` and check `Origin`,
  so a page on another site can't make a logged-in browser change them: browsers send basic
  credentials automatically, which is what makes cross-site requests a risk.
* The page sets a strict Content Security Policy (`default-src 'self'`), since everything is
  served locally.

### 5.5 Read-only by the database, not by the client

Today the dashboard connects as the same ClickHouse user as the ingester and asks for
`readonly: 2` in its query settings. A bug that dropped the setting would hand the page
write access to everything. Instead:

* A ClickHouse user `undercurrent_web`, defined in `clickhouse/users.d/web.xml` with its
  password from the environment (`WEB_CLICKHOUSE_PASSWORD` in `.env`), with `SELECT` on the
  database and the `system` tables the Collection page reads, and, from phase 5, `INSERT` on
  `web_pins` and `web_views` only.
* A settings profile for it, so the dashboard can't starve the analyzer on the shared
  machine: `max_threads` 2, `max_memory_usage` 1 GB, `max_execution_time` 30 s,
  `max_concurrent_queries_for_user` 6, `priority` 10 (the analyzer's queries win), and
  `readonly` 2 as a second guard until writes exist.
* The `web` service gets only this user's credentials, as today it gets no other secrets.
* CI's ClickHouse service can't mount the users file, so the tests create the same user with
  SQL (`CREATE USER`, `GRANT`, `CREATE SETTINGS PROFILE`), and one test checks that it can't
  write.

Grafana's unit is the dashboard: panels side by side that share variables. The rebuild's
unit is the entity: a term, a scope, a story, an edge, a product, each with a page and a
url, shown the same way wherever it appears and linked to everything related.

Every entity has one component that renders it everywhere (`TermChip`, `ScopeChip`,

sparkline and whether it's trending now; a scope's volume and top trend; an event's cascade
in one line. The current drawer becomes a **peek**: a side sheet with the term page's top
half, opened by a click, kept in the url (`?peek=word:claude`), expanded to the full page
with one more click.

### 6.2 The term page

`/t/{kind}/{term}?scope=tech&range=30d`, the page an alert opens. From top to bottom:

1. **Header:** the term, its kind, the scope picker, and a status line: "trending in tech
   (z 9.4, 12× usual), 3 of 9 channels" or "emerging in r/localllama over 13 weeks (+21% a
   month)", whatever is true; pin and export buttons; links to Grafana and to the platform's
   search.
2. **Share over time** with every annotation: alerts sent, the scored runs where it trended
   (a band per run), event onsets per scope, forecast windows (expected time with the lag's
   IQR, due-by), the long-term window, the Wikipedia onset. A brush sets the range.
3. **Why it's trending** (when it is): the explainer of §7.1.
4. **Where:** a bar list of channels (share and people), next to small multiples of the term
   in each channel of the scope, sorted by when it crossed (§7.1).
5. **Spread:** its events as cascades, the latest one with a replay (§7.1), the forecasts
   pending for it.
6. **Long-term:** its weekly share and category per window and scope.
7. **Related:** co-occurring terms of the last 48 hours, and for products their intents
   (switches in and out, complaints, alternatives).
8. **Rhythm:** hour of week and calendar heatmaps.
9. **Comments:** the last 48 hours, with the term and any intents highlighted.

Each section asks its own endpoint, so the page renders top first, and sections without
data say so in one line instead of taking space.

### 6.3 The other pages

* **Scope** (`/s/tech`): volume and people over time, members with their shares of the
  volume, what's trending now and long term, its distinctive vocabulary against the
  platform (§7.1, later), edges where its channels lead or follow, its intent summary.
* **Event** (`/e/word/llama 4/2026-11-20T08:00Z`): the cascade as a timeline (scopes in
  onset order, with the time since the first), the replay on the network, every scope's
  share over the span as small multiples, forecasts made during it and how they turned out,
  the Wikipedia onset.
* **Edge** (`/edges/all/r/localllama/tech`): the numbers of ARCHITECTURE.md §4.6 explained
  in words ("tech picks up 62% of r/LocalLLaMA's terms, 3.1× its usual rate, after a median
  18 hours"), the lags as a strip plot, the training events as a list of cascades, its
  forecasts and how they turned out.
* **Product** (`/p/notion`): flows in and out (Sankey and net flow), considering, complaints
  and alternatives over time, the reasons once the churn radar has them, comments. With a
  radar watchlist, its competitors side by side. This is the churn radar's report page in
  waiting.
* **Alerts** (`/alerts`): every alert and forecast alert sent, newest first, each with its
  explainer one click away.
* The **current six pages** stay as the entry points (Trending, Long-term, Why people
  switch, Early warning, Explore, Collection), linking into the entity pages.

### 6.4 Cross-filtering and linked brushing

Within a page, the selection is shared and lives in the url:

* **Time:** brushing any time chart sets `from`/`to` for the whole page.
* **Scope:** clicking a channel in "Where" narrows every chart and the comments to it;
  clicking again goes back to the group.
* **Terms:** hovering a row or a legend entry emphasizes that series in every chart;
  clicking adds it to the highlighted set (`hl=`), shift-click compares it in Explore.
* **Crosshairs** are linked across the charts of a page and across small multiples.

### 6.5 Across pages

* The scope stays when moving between pages that are about a scope, as today (TanStack
  Router's retained search params).
* Breadcrumbs on entity pages show where the reader came from (Trending → claude → its
  event), from the url's `from=` parameter, not from history, so a shared link shows the
  same.

### 6.6 Command palette

`⌘K` (and `/`) opens a palette over every page:

* **Pages and actions:** go to Trending, toggle dark mode, copy link, export this chart.
* **Scopes:** every platform, group and channel, from `meta`.
* **Terms:** prefix search over `term_catalog`, a table kept by refreshable materialized
  views: every term that ever trended, emerged, had an event or a forecast (refreshed every
  hour), and the 200,000 most mentioned terms of the last 90 days (rebuilt once a day), with
  kind, last seen and mentions. It stays small (under a million rows) and answers a prefix
  in milliseconds. A term that isn't in it still opens: Enter on what was typed goes to its
  page, which works for any term.
* Recent and pinned terms first.

### 6.7 URL state

Every view is a link. Each route's search params are a Zod schema with defaults, and
defaults are left out of the url, so links stay short:

```
/trending?scope=tech&horizon=6h&kinds=word,phrase
/t/word/claude?scope=tech&range=30d&hl=claude,anthropic&peek=
/explore?terms=claude,gemini&scope=tech&from=2026-11-01&to=2026-11-14&bucket=hour&rate=macro
/e/phrase/llama%204/2026-11-20T08:00Z?at=2026-11-21T14:00Z      (replay position)
/trending?scope=reddit&as_of=2026-12-01T12:00Z                   (time travel)
```

Invalid values fall back to defaults with a notice instead of an error page, so old links
keep working after a parameter changes. Sort orders, table pages, the table view and open
sections are in the url too; only purely visual state (a hover) isn't.

### 6.8 Links in

* Alerts, digests and forecast alerts (`notify/messages.py`) link to the web dashboard once
  the term page exists: the term page at the scope and run of the alert. A setting
  `notify.links: web | grafana` (default `web` from phase 3) with `WEB_URL` next to
  `GRAFANA_URL`; the message keeps a second link to Grafana.
* Grafana's tables link to the term page too (a link column in the builder), so the pro mode
  and the dashboard reach each other both ways.

## 7. Beyond Grafana

### 7.1 The list, in order of value for the effort

Grafana shows a query's result in a panel. It can't build a page around an entity, animate
a network, lay out flows, or explain a number with the code that made it. Each item below
says what it needs and what it costs at production scale. P1 comes with the connected data
(phase 3), P2 next (phase 4), P3 when wanted.

**P1**

1. **The term page and its links** (§6.2). Needs only the endpoints of §5.2. Every query is
   a key range on `(channel, term)` or `(horizon, scope, term)` except the term's scored
   runs across all scopes: `trends` is ordered by scope first, so finding one term in 90
   days (about 50 million rows) reads the whole `term` column, 1–2 s. A bloom filter skip
   index on `trends.term` (a migration; a few MB) brings it to milliseconds.
2. **"Why is this trending."** For a trend row, show what the score is made of:
   * the share now (`mentions / total`) against the share before (`reference_mentions /
     reference_total`) as a dumbbell, with the platform's share as a third dot;
   * how far the prior pulled each side (`prior`, from the stored `log_odds` and the raw
     shares), and the uncertainty behind `z`;
   * the gates as a checklist with the values: mentions ≥ 10, people ≥ 5, ratio ≥ 2, z ≥ 3,
     days of history, breadth for groups, from the config's gates for that scope and kind;
   * the alert's outcome and why (sent, cooldown since the earlier alert, daily cap,
     warm-up, muted, subsumed by a phrase, with the phrase);
   * the member channels that trend in the same run (breadth), with their z;
   * three comments and the top co-occurring terms (item 9).

   Everything is stored in `trends` already; the explainer recomputes `δ` and `σ` with
   `detect/scoring.py` to show the parts, so it can never disagree with the detector. Cost:
   one key range per scope, milliseconds.
3. **Annotations on every series**: alerts, runs, onsets, forecast windows, long-term
   windows, Wikipedia onsets. From `notifications`, `trends`, `lead_lag_events` (ordered by
   kind and term), `forecasts` (kind, term), `long_term_trends`, `wiki_leads`. Milliseconds
   per term.
4. **The alerts inbox** and its links (§6.3). `notifications` and the rows behind them.
5. **Command palette, keyboard navigation, exports** (§6.6, §4.4): client-side, apart from
   `term_catalog`. Its most mentioned terms come from 90 days of `term_daily`, about 270
   million rows: an estimated 10–20 s on 2 threads at production scale, so once a day at a
   quiet hour. The terms that trended are added every hour from `trends`, which is cheap.

**P2**

6. **Propagation replay.** On an event page, a play button and a scrubber step through the
   event's span hour by hour: every scope on the network fills with its share of the term, a
   ring marks the hour it crossed its onset, the edges that predicted it light up with the
   actual lag against the expected one, and followers not reached yet show their forecast
   probability. Speed, pause, step, and the hour in the url (`at=`). With
   `prefers-reduced-motion`, it steps without animation. Needs the event (one row of
   `lead_lag_events`), the edges of its topic (one day of `propagation_edges`), and the
   term's hourly counts in every analyzed channel over the span: 46 channels × 17 days × 24
   hours, about 19,000 rows by `(channel, term)` key ranges, with `scope_hourly` for the
   shares. Groups are summed from their members in the API. Under 200 ms. The network's
   layout puts scopes in columns by their median onset lag from the first mover across all
   events, so left-to-right is the usual direction of spread and the replay reads as a wave.
7. **The spread map.** The network of edges (width by lift, label with the median lag, color
   by topic, the IQR on hover) with a topic filter, beside a leader × follower heatmap of
   lift or lag for when the graph gets dense. After cross-platform phase 3, the platform map
   (platforms as nodes, median lags, first-mover shares) on the same component. Data: one
   day of `propagation_edges`, a few hundred rows.
8. **Switching flows.** A bipartite Sankey (products on the left as "from", on the right as
   "to", so flows both ways don't form cycles), a chord diagram as the alternative view, and
   net flows per product as diverging bars (in − out). Below 10 the counts are counts, never
   percentages, as the churn radar's rule says. Data: `term_daily` with `kind = 'switch'`
   over the range. `kind` isn't in the sorting key, so 30 days read the `kind` column of
   every row of the scope's channels, about 50 million rows for `reddit`, about 0.2 s; the
   switch rows themselves are few. The product page's "every switch into notion" can't use
   the key (`… → notion` sorts by the other product) and reads every switch term; if that
   measures over a second on the benchmark database, an `intent_daily` table keyed by
   product (a materialized view from `term_events`, a few MB a year) fixes it.
9. **Co-occurring terms.** For a term and scope, the terms mentioned most in the same
   comments of the last 48 hours, ranked by how much more often they appear with the term
   than without it (the same weighted log odds as the detector, comments with the term
   against the scope's 48 hours from `term_hourly`). The comments are found in `items` with
   the same matching as Explore's mentions; their text goes to Python and through the
   ingester's own term extraction, so related terms are terms as the detector counts them
   (phrases, domains, intents included), not a SQL tokenizer's approximation. Measured on
   2026-10-31 with 40,000 items: the scan for a term took 5 ms, tokenizing in SQL 16 ms. At
   a million items, about 25 times that, 0.1–0.4 s for the scan, plus up to 2,000 comments
   through the Python tokenizer, about 0.2 s. Cached for 15 minutes. It only exists for the
   last 48 hours (the text is gone after that), which the section says. A `tokenbf_v1` skip
   index on the text, or ClickHouse's full-text index if it's stable in the version we run,
   brings the scan to milliseconds if needed.
10. **Small multiples across scopes:** one term in every channel of a group, sorted by when
    each crossed, with a shared or an indexed y axis. The static version of the replay.
    `(channel, term)` key ranges: 46 channels × 365 days is 17,000 rows. Cheap.
11. **Bump chart of ranks:** a scope's top 10 over the last 7 days, from `trends.rank`, one
    point an hour. `(horizon, scope)` is the key prefix: 7 days × 96 runs × 50 rows, 34,000
    rows. Cheap.
12. **Rhythm:** a term's share by hour of week over 28 days, divided by the scope's own
    rhythm, so it shows when the term is talked about more than the scope talks at all
    (morning terms, US vs European hours), and a calendar of a year of daily shares.
    `term_hourly`: 46 channels × 672 hours; `term_daily`: 46 × 365. Cheap.
13. **Forecast record:** the calibration plot with Wilson intervals per bin and the base
    rate for comparison, lead times as a strip plot, the record per edge. `forecasts` is
    small.
14. **What's arriving:** pending forecasts as a timeline per follower: the expected time
    with the IQR as a bar and the due-by as a whisker, the probability as the label. Same
    data as today's forecasts table.
15. **What-if gates:** sliders for min mentions, people, ratio and z over the stored trends
    of a run, recomputed in the browser, showing what would have trended or alerted. It only
    sees the rows the detector stored (the top 50 per scope), which it says. Free; useful
    for tuning `config.yaml` without the replay harness.

**P3**

16. **Time travel** (`as_of`, §5.2): any page as of a past time, as far as the stored
    history goes: trends for 90 days, edges for 180, events and long-term trends forever. It
    comes with the `now` parameter, so the cost is the date picker and making every page
    honest about what it can't show for the past (the 48-hour comments).
17. **Pinned terms and saved views.** Pins are a short list of terms followed on purpose:
    shown first on Trending, in the palette, and on a "Pinned" page with small multiples.
    Saved views are named urls. Both in two small ClickHouse tables (`web_pins`,
    `web_views`, ReplacingMergeTree with a deleted flag), written through the web user's
    narrow grant, so they're the same on the laptop and the phone, and the analyzer can read
    pins later (an alert when a pinned term moves at lower gates). Not called watchlists:
    the churn radar's watchlists are products in `config.yaml`, a different thing.
18. **Distinctive vocabulary** of a scope, or of two scopes against each other: the log odds
    of a scope against its platform (ARCHITECTURE.md §4.4), shown as a slope chart. A group
    of 10 channels over 28 days aggregates about 30 million `term_daily` rows by term:
    2–5 s and several hundred MB at production scale, so it's computed once a day by the
    analyzer into a small table, not on request.
19. **The churn radar's weekly report** as a page, with every number opening its threads
    (`intent_items`), once its phase 4 exists.
20. **An LLM's explanation** on the term page, once ARCHITECTURE.md §4.5 is built and
    switched on.

Left out: maps (there's no geography in the data), 3D, and anything that needs raw text
older than 48 hours.

### 7.2 What it costs the machine

The dashboard shares the 4-CPU, 8 GB machine with the ingester and the analyzer, which
matter more. So:

* every endpoint has a measured cost on the benchmark databases before it ships (§10.4),
  with a budget of 1 s and 500 MB at production scale, or it's precomputed;
* the web user's profile (§5.5) caps threads, memory and time and gives the analyzer
  priority;
* the in-process cache and `Cache-Control` absorb reloads;
* the precomputed tables (`term_catalog`, distinctive vocabulary, maybe `intent_daily`) are
  small and refreshed hourly or daily.

## 8. Design system, accessibility, dark mode, mobile

### 8.1 Design system

* **shadcn/ui** components on **Tailwind v4**, themed by CSS variables: the semantic tokens
  of [BRAND.md](BRAND.md) §5.3 and §7 (surfaces, ink, borders, the Current accent), with
  shadcn's own variable names mapped onto them, so the UI and the charts share one set of
  tokens (§4.5). Light and dark set on `<html>` before the first paint (as `index.html`
  does today), following the system until the reader picks.
* **Type** (BRAND.md §6): IBM Plex Sans for interface and numbers, its figures tabular by
  default; IBM Plex Mono for raw terms, commands and config keys; Source Serif 4 only for
  reports and slides, never in the app. Self-hosted from Fontsource, bundled by Vite, so
  nothing loads from a font CDN.
* **Density** (BRAND.md §7): rows and controls 32 px, 13/18 text in data views and 14/20
  elsewhere, radii 4/6/8, hairlines instead of shadows; 44 px touch targets on phones.
* **Building blocks** beyond shadcn's: `Panel` (title, subtitle, help, actions, the frame
  every chart and table sits in), `StatTile` and `KpiRow`, `DataTable` (TanStack Table with
  sorting, column visibility, CSV export, virtualization, sort in the url), `ScopePicker` (a
  combobox grouped into platforms, groups and channels, with each group's members),
  `RangePicker` (presets as rows, a custom range behind a hairline, per the dataviz spec),
  the entity chips and hover cards (§6.1), `EmptyState` (§8.4), `Kbd` hints.
* **Copy** in the project's voice: plain, short, numbers with their meaning ("12× its usual
  share"), help texts carried over from today's page and the Grafana descriptions.

### 8.2 Accessibility

WCAG 2.2 AA as the bar:

* shadcn's Radix primitives handle focus, keyboard and ARIA for menus, dialogs, popovers and
  tabs.
* Every chart has a title and a description, a table view, and identity never by color
  alone: legends for two or more series, direct labels for up to four, line keys in
  tooltips, icons with every status color. Canvas charts are opaque to screen readers, so
  the table view is the accessible version, one keystroke away.
* Texture (ECharts decals) under `forced-colors`, in print, and as a setting.
* `prefers-reduced-motion` turns off chart animation and makes the replay step.
* Playwright runs axe on every page in both themes, and one test walks the main flows by
  keyboard only.

### 8.3 Dark mode

Dark is a selected palette: the dark steps of §4.5, validated against the dark surface, not
a filter. Charts re-theme in place when the mode changes (no reload, no lost zoom). Every
visual test runs in both modes.

### 8.4 Empty, early and small

For months most pages will have little or no data, so empty states are designed, not
leftovers:

* `meta` returns **readiness** per feature from the stored history: "Long-term trends from
  Monday 2027-02-01 (13 complete weeks)", "Edges from about early December: an event takes
  17 days to close, a pair needs 5", "Comments: the last 48 hours".
* A section without data takes one line, not a panel of nothing.
* Warm-up is shown where it matters: today's first-day effect (German stopwords trending in
  `reddit`) gets a banner explaining that the score compares with the platform until 28 days
  of history exist.

### 8.5 Mobile

The most common mobile path is an ntfy alert on the phone opening the term page, so the term
page is designed phone-first:

* Navigation collapses to a bottom bar with the main pages and the palette.
* Tables become lists of cards with the two or three numbers that matter and a sparkline.
* Charts take the full width with fewer ticks; a tap shows the tooltip, a second tap opens
  the entity. Brushing becomes a range picker.
* The peek becomes a full-height sheet.
* Playwright runs the main flows at 390 × 844 in WebKit as well as at desktop size in
  Chromium.
* A web app manifest, so it can be added to the home screen. No service worker caching data:
  stale numbers on a phone would mislead.

## 9. Build and deploy

### 9.1 The image

One `Dockerfile`, more stages; Compose's `web` service builds the `web` target, the ingester
and the analyzer build the default one, and BuildKit only builds the stages a target needs:

```dockerfile
FROM node:26-slim AS web-build
WORKDIR /web
RUN npm install -g pnpm@12.16.1                  # Node 25+ no longer ships Corepack
COPY web/package.json web/pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile
COPY web/ ./
RUN pnpm build                                   # → /web/dist

FROM python:3.13-slim AS base
# … uv and the Python dependencies, as today …

FROM base AS web
COPY --from=web-build /web/dist /app/web-dist
CMD ["undercurrent", "web", "--host", "0.0.0.0"]

FROM base AS app                                  # the default, last
CMD ["undercurrent", "ingest"]
```

`.dockerignore` leaves out `web/node_modules`, `web/dist` and the v1 leftovers.

### 9.2 Serving

The FastAPI process serves everything on port 3610, as today:

* `/api/v1/*`: the API.
* `/assets/*`: the built files, named by content hash, cached for a year (`immutable`).
* Every other path: `index.html`, never cached, so the router handles deep links (`/t/word/
  claude` after a reload).
* Compressed at build time (`.br` and `.gz` next to each file, served when accepted), basic
  auth in front of all of it, the security headers of §5.4.
* `undercurrent web --dev` serves only the API, for the dev server.

A separate static server (Caddy, nginx) would only add a container; it's worth it if a
reverse proxy with TLS is put in front anyway (§5.4), which can then serve `web-dist` too.

### 9.3 Developing

* `docker compose up -d` runs the stack as today, the API on 3610 with the last built page.
* `cd web && pnpm dev` starts Vite on **3611**, proxying `/api` to 3610: the page with hot
  reload on live data, no Python needed.
* For API work: `uv run undercurrent web --dev --port 3612 --reload`, and
  `UNDERCURRENT_API=http://localhost:3612 pnpm dev`.
* Against the demo database (§10.2): the same with `CLICKHOUSE_PORT=3617
  CLICKHOUSE_DB=undercurrent_demo`.
* Without any ClickHouse: `pnpm dev:mock` serves the recorded fixtures through MSW.
* `pnpm gen:api` after any change to a model.

### 9.4 CI

`.github/workflows/ci.yml` gets two jobs next to `check`:

```yaml
  web:
    runs-on: ubuntu-latest
    defaults: {run: {working-directory: web}}
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: {node-version-file: web/.nvmrc, cache: pnpm, cache-dependency-path: web/pnpm-lock.yaml}
      - run: pnpm install --frozen-lockfile
      - run: pnpm typecheck                  # tsc --noEmit, TypeScript 7
      - run: pnpm lint                       # oxlint with type-aware rules
      - run: pnpm format:check               # biome format
      - run: pnpm test                       # vitest, including chart SVG snapshots
      - run: pnpm build
  e2e:
    needs: [web]
    runs-on: ubuntu-latest
    services:
      clickhouse: …                          # as in `check`
    steps:
      - …checkout, uv, pnpm as above…
      - run: uv run undercurrent web openapi > web/src/api/openapi.json
      - run: cd web && pnpm gen:api && git diff --exit-code   # API and types agree
      - run: uv run python bench/demo.py seed --database undercurrent_demo --small
      - run: cd web && pnpm build && pnpm exec playwright install --with-deps chromium webkit
      - run: uv run undercurrent web --port 3610 & cd web && pnpm e2e
      - uses: actions/upload-artifact@v4     # traces and screenshots, on failure
        if: failure()
```

`check` keeps running pytest, now including the API's models and every endpoint on the
schema; `docker build .` becomes `docker build --target web .` and `docker build .`.

## 10. Testing and demo data

### 10.1 Layers

| Layer | Tool | What |
| --- | --- | --- |
| API | pytest, throwaway databases as today | every endpoint on the schema, models validate, parameters refuse bad input, `now` makes results deterministic, auth, the read-only user can't write |
| Contract | CI's schema and type diff | the page and the API agree |
| Units | Vitest | formatting, url schemas (parse, defaults, round trip), data transforms (filling buckets, net flows, rank lines), color assignment |
| Charts | Vitest + ECharts' server-side SVG | each option builder on fixed data, rendered to SVG and snapshotted; a broken chart shows up as a diff an agent can read |
| Components | Vitest browser mode with Playwright, MSW fixtures | pickers, tables, the palette, the peek, empty states |
| End to end | Playwright against the API and the demo database | each page loads; url state survives a reload; brushing changes the url; the palette finds a term; an alert's link opens the term page; the replay plays; mobile layout; axe in both themes |
| Visual | Playwright screenshots in CI's Linux image, time frozen | the main pages and every chart form, light and dark |

### 10.2 The demo database

The live database will be thin for months (§1), and visual tests need the same data every
time. `bench/demo.py seed --database undercurrent_demo` builds a complete, deterministic
history into a ClickHouse of its own (the bench container on port 3617, never the live one):

* **The history:** 120 days of hourly and 400 days of daily counts for the configured
  channels at a tenth of production volume (enough for every detector to find what's
  planted), or with `--small` 30 days and the channels of two groups, for CI in about a
  minute. From the Zipf vocabulary of `bench/synthetic.py`, but with **readable terms** (a
  bundled word list instead of `w000000123`) and **numpy's seeded random numbers instead of
  ClickHouse's `rand()`**, which today makes the bench's output differ on every run.
  Production-scale cost stays the job of the existing bench databases (§10.4).
* **Planted stories**, so every chart has something to show: bursts that spread from a
  leader to followers with lags (cascades for the replay), terms that emerge, mainstream,
  fade and spike once over 13 and 26 weeks, switching flows between products with a
  complaint spike, needs, a coordinated launch, an ingestion gap.
* **The real code on top:** the detectors run over it as of every hour of the last days
  (`undercurrent replay --store`, planned in cross-platform phase 2; this step adds the
  option if it isn't there yet), the long-term detector
  as of each Monday, lead–lag backfill for events, edges and forecasts. The trends, edges
  and forecasts on the demo come from the same code as production, not from rows written by
  hand.
* **48 hours of items** with generated sentences (templates around the planted terms and
  intents, never real Reddit text), so comments, intents and co-occurring terms work.
* **Frozen time:** the seed ends at a fixed `as_of`, and the API runs with
  `UNDERCURRENT_NOW` set to it in tests, so screenshots don't change from day to day.

`undercurrent web record --out web/tests/fixtures` saves every endpoint's response from the
demo database for MSW (component tests, `pnpm dev:mock`).

### 10.3 With little real data

* Develop and review on the demo database; check on live data what it has.
* Empty states with readiness (§8.4) are tested on an empty database in e2e too.
* The first real edges (around early December) and long-term trends (2027-02-01) are
  checkpoints to look at the pages on real data and adjust.

### 10.4 Measuring cost

`bench/web.py` calls every endpoint against the production-scale benchmark databases
(`undercurrent_bench` for a year of daily history, `undercurrent_bench_ll` for hourly
history with events) on the 4-CPU, 8 GB bench container, and reports per endpoint the time,
peak memory and rows read from `system.query_log` (by `log_comment`). An endpoint over its
budget (§7.2) is fixed or precomputed before it ships. In production, the same numbers come
from the query log, and the Collection page shows the dashboard's own cost per endpoint.

## 11. Migration and coexistence with Grafana

### 11.1 Parity first

Nothing the current page or Grafana shows gets lost. A parity table in the pull request of
each step maps every page of the current dashboard and every Grafana panel to where it is in
the new one:

| Today | Grafana | New |
| --- | --- | --- |
| Trending: scored trends, top trends chart, digest, alerts | Trending now (8 panels) | `/trending`, `/alerts`, the term page's explainer |
| Trending: Quick look | Rising (1) | `/trending?view=quick` |
| Long-term | Long-term trends (9) | `/long-term`, the term page |
| Why people switch | Intent radar (13) | `/intents`, `/p/{product}` |
| Early warning | Early warning (14) | `/spread` (forecasts, cascades, the map), `/e/…`, `/edges/…`, `/forecasts` |
| Explore, the term drawer | Term explorer (5) | `/explore`, `/t/…` and its peek |
| Collection | Ingestion (9) | `/collection` |

### 11.2 Steps

1. **API first, page unchanged** (phase 1): FastAPI serves today's page and the new
   `/api/v1/`, and keeps today's `/api/<name>` endpoints as aliases while the old page
   needs them. The old page keeps working throughout.
2. **The new page beside the old one** (phase 2): the TypeScript app at `/`, the old page at
   `/classic/` until the new one has reached parity and been used for a while; `static/` and
   the old endpoints are deleted in phase 3.
3. **Links:** "Pro mode ↗" on every view maps the view's state to the matching Grafana
   dashboard and variables (today's `grafana.js`, typed, with the `undercurrent-*` uids);
   alerts switch to web links (§6.8).

### 11.3 Grafana as the pro mode, and deciding

Grafana stays, unchanged, while both exist: ad-hoc SQL, panel editing and Grafana's own
explore are things the dashboard won't do. The rule of the README stays: a change to a
panel's numbers belongs in both (the API's query and the builder's panel). To catch drift, a
test on the demo database compares the headline numbers of a few panels with the API's (top
trends, long-term counts, edges, forecast precision).

Deciding which to keep, after the dashboard covers everything (phase 4) and four weeks of
daily use:

* if the user no longer opens Grafana (its usage stats, and the dashboard's own request
  log), remove it: the container, `grafana/` with its 2,307-line builder and 7 dashboards,
  the plugin, and the double maintenance;
* if Grafana stays for ad-hoc work, stop porting new panels to it, and keep the existing
  ones until they break.

## 14. Risks

* **Two toolchains.** Node, pnpm and a few dozen npm packages next to Python and uv, each
  with its own updates and supply-chain risk. Kept small: few direct dependencies, pinned,
  install scripts off, a minimum release age, grouped weekly updates.
* **Owners change.** In 2026 alone React moved to a foundation, Cloudflare bought Vite's
  company (and Astro), Tailwind's company let go three of its four engineers and may join
  Shopify, and TypeScript 7 left the tools that depend on its API behind until 7.1. The
  picks favor
  foundations (React, Apache ECharts) and tools used so widely that they'd be forked rather
  than dropped, and keep each replaceable: Tailwind behind CSS variables, the API client
  generated from a standard schema, linting and formatting by separate tools.
* **Double maintenance with Grafana** until the decision; the drift test and the "change
  both" rule contain it, the decision ends it.
* **Dashboard queries on the shared machine** at production scale; the profile's caps, the
  benchmark per endpoint and precomputed tables are the counters.
* **ECharts isn't shadcn-native.** Its look depends on our theme and option builders; done
  once in the kit, it holds. Canvas charts need the table views for accessibility, which the
  kit makes impossible to forget.
* **Building for an empty database.** Most of §7 can't be judged on live data for weeks; the
  demo database plants what the real data should show, and the checkpoints of §10.3 compare
  it with reality.
* **Too much for one user.** Each phase stands on its own; stopping after phase 3 leaves a
  better dashboard than today's.
* **Parallel work in the checkout.** The rebuild touches `src/undercurrent/web/`, the
  Dockerfile, Compose, CI and `notify/messages.py`; it runs after the rename, and new
  platforms only change what `meta` returns, since nothing tells channels apart by prefix.

## 15. Decisions

Asked as open questions; the user took each recommendation on 2026-11-01:

1. **The front end lives in this repository**, in `web/`, with Node and pnpm next to uv.
2. **ECharts as the chart engine**, behind our own kit and themed to match (§4.3).
3. **Pins and saved views on the server** (`web_pins`, `web_views`), the same on every
   device and readable by alerts later.
4. **Alert links** move from Grafana to the term page once it exists (§6.8).
5. **Reaching it from the phone** stays as today: localhost, an SSH tunnel and basic auth.
   Nothing beyond basic auth is built.
6. **Grafana** stays as the pro mode; decide after four weeks of using the new dashboard
   (§11.3).
7. **The v1 leftovers** (`node_modules/`, `packages/`, `config.json`, `v2/`, untracked) are
   deleted only with the user's OK, since that can't be undone; until then `tsconfig.json`
   names its `types`, so they're never picked up.
8. **Time travel and the what-if gates** are built (P3 and P2).

## 16. Order of work

Each step is committed on `develop` with the tests green, and runs while no other session
edits the same files.

1. **Groundwork** (half a day): the answers to §15, the leftovers deleted, Node pinned,
   `web/` scaffolded with its tooling and `AGENTS.md`.

   today's endpoints as typed `/api/v1/` routes with `now` and `null`, and the aliases.

   Query and the generated client, `<Chart>`, `TimeSeries`, `BarList`, `Heatmap`, the
